# 구매 연결: 전체 스키마 검증과 재확인 운영 조건

상태: PR #115 Draft, 운영 미적용. 상품·옵션 동일성, 판매 옵션의 현재 유효성, 재고, 가격은 서로 다른 사실이다.
이 문서는 만료 기간을 늘리거나 운영 연결/근거를 생성하지 않는다. UI·공개 CTA·가격 연동도 이번 범위가 아니다.

## 1. 검증 기준과 발견한 문제

- 검토 기준 HEAD: `5827b905758315ff654ec2be80fb198ca4d587e0`.
- 해당 SQL 초안 SHA-256: `a72c1793f6fb9b6ed481f6e941e431e56a3b8739c6837c31daa15565b5dd5634`.
- 기존 로컬 bootstrap으로 저장소 historical migration 70개(임시 로컬 guard 2개 추가)를 적용한 뒤,
  기준 초안의 RLS·RPC 권한·공개 projection·실제 제품/감사 테이블과의 정상 저장은 통과했다.
- **실제 결함 재현:** 제품의 중량 필드가 달라지면 공개 조회는 연결을 숨겼지만, 최신 expected_revision으로
  과거 target 관찰을 다시 제출하면 저장이 성공했다. 이름/브랜드만 같으면 바뀐 상품 식별정보에 오래된 근거를 재사용할 수 있었다.
- 수정: target 관찰의 `extracted_data.purchase_product_identity_v1`에 검토 시점의 제품 식별 스냅샷을 요구한다.
  내부 `purchase_product_identity` 함수가 현재 제품의 name/brand/variant/weight/barcode/display_name/canonical_key/
  pet_type/life_stage/formulation을 같은 형태로 생성한다. 공개 조회와 verified 저장 모두 이 스냅샷과 현재 제품의 일치를 검사한다.
  누락·변경이면 자동 생성/보정하지 않고 거부한다. 새 검토 근거가 필요하다.
- 스냅샷은 관찰 당시 증거여야 하며, 실패 후 현재값을 복사해 과거 관찰을 고치는 방식으로 갱신하지 않는다.
  정상적인 별도 관리자 관찰 수집/검토 경로에서 새 관찰을 남겨야 한다. 이 데이터 구조를 실제로 채우는 UI/운영 수단은 아직 없다.
- 이것은 문자열/식별 스냅샷의 엄격한 비교다. 포장 이미지의 진실성이나 단위/상품 의미를 자동 판정하는 엔진이 아니다.

## 2. 전체 저장소 스키마 검증 방식

`npm run test:purchase-links:schema`는 CI PostgreSQL 17의 두 빈 로컬 DB만 허용한다.
host/user/DB 이름을 고정 검사하며 production project/connection/secret은 받지 않는다.

1. 원문 migration만 replay하는 DB에서 최초 실패를 기록한다. 알려진
   `20260611151005_supplement_image_label_ingredients.sql`의 기존 제품 FK 의존성(23503) 외 실패는 무시하지 않는다.
2. 다른 DB에는 기존 `prepareLocalSupabase`를 사용한다. historical SQL의 version/name/bytes를 그대로 복사하고
   원문 해시를 검사한다. 기존 local-bootstrap guard가 알려진 orphan 47개만 건너뛰며 dummy product를 만들지 않는다.
3. 복원 스키마 위에 `migration_drafts`의 초안만 명시적으로 실행한다. 자동 migration 경로에는 추가하지 않는다.
4. 실제 products/product_observations/admin_audit_log와 정책 위에서 다음을 검증한다.
   - anon/authenticated 쓰기 및 private table 읽기 거부, service_role RPC 허용/직접 UPDATE 거부
   - reviewed/verified·비노출·verified-only 설정에 맞는 공개 반환, 최소 필드 projection
   - 전체 제품 컬럼 보존, 감사 원자성/감사 실패 롤백, 재전송·충돌의 무변경
   - 제품 식별 스냅샷 변경·관찰 current 변경·만료 시 공개/저장 일관성, 새 근거로 재승인
   - 기존 cleanup RPC 정상 적용 및 그에 따른 연결 무효화
   - 기존 컬럼/함수/정책 정의가 초안 적용 전후 동일
5. 역사 migration·운영 ledger에는 아무 변경도 하지 않는다. 데이터는 모두 합성이다.

Auth/Storage는 기존 테스트와 동일한 최소 service-schema fixture다. 실제 GoTrue/Storage/PostgREST HTTP,
Supabase 전체 서비스 설정이나 운영 제품/권한을 검증한 것은 아니다. 별도 실 Supabase 사전 검증은 출시 조건으로 남는다.
로컬 PGlite로도 같은 전체 schema assertion을 실행하며, 네이티브 Mac Rollup/Vitest는 재실행하지 않는다.

### 기존 삭제 경로의 원자성 수정 (초안, 운영 미적용)

첫 버전 정책: **상태/만료 여부와 무관하게 구매 연결 행이 하나라도 있는 제품은 물리 삭제를 거부한다.**
운영자는 기존 `setProductVisibility`로 비노출 처리한다. 연결·관찰·감사를 cascade 삭제하거나 이름을 바꾸지 않는다.
비노출은 삭제/복구가 아니며 기존 판정·이력은 남는다.

기존 `putInTrash` → HTTP DELETE → audit의 분리 처리는 제품 삭제에서 제거한다.
인증된 admin-write `deleteProduct`는 service_role 전용 `admin_delete_product(uuid,text)` 하나만 호출한다.
DB 함수는 제품 행을 FOR UPDATE로 잠근 뒤 모든 연결 이력을 확인한다. 거부는 HTTP409와
`purchase_history_exists`로 반환하며 휴지통/감사를 쓰지 않는다. 연결 저장 함수도 같은 제품 행을 잠근다.
연결 생성이 먼저면 삭제가 거부되고, 삭제가 먼저면 이후 연결 생성이 제품 없음으로 실패한다.
단순 클라이언트 사전 조회나 FK 오류 처리만으로 경쟁을 막는 방식이 아니다.

연결 없는 제품은 동일 트랜잭션에서 제품/자식 스냅샷, 휴지통 삽입, 제품 삭제, 감사를 처리한다.
스냅샷 대상은 기존과 동일한 제품·성분 연결·영양 프로필·리뷰이며 자식 행도 잠근다.
FK·휴지통·감사 오류는 전체를 롤백한다. 동시 삭제 요청은 한 번만 삭제/기록하고 나머지는 not_found다.
기존 ingredient 삭제·휴지통 복구를 재작성하지 않으며, 복구 전체/실제 Supabase HTTP는 별도 검증 범위다.
이력 보존 FK의 RESTRICT와 서비스 역할 직접 쓰기 제한도 유지한다.

**배포 의존성:** SQL은 계속 migration_drafts다. 검토된 DB 함수/권한을 먼저 준비하지 않고 이 admin-write를
배포하면 기존 제품 삭제도 새 RPC 부재로 실패한다. 자동 fallback으로 비원자적 옛 삭제를 실행하지 않는다.
이번 PR은 적용/배포하지 않으며 실 Supabase HTTP·정상 삭제/거부 UI smoke는 이후 출시 게이트다.

| 축 | 현재 구현/만료 효과 | 권고 운영 방식 및 남은 결정 |
| --- | --- | --- |
| 판정 제품의 동일성 | 제품 식별정보·관찰 스냅샷이 바뀌면 즉시 공개 제외 및 오래된 근거 재승인 거부 | 상품 내용이 안정적이어도 변경 감시 필요. 스냅샷이 같을 때만 target 근거를 재사용. 포장/개정 변경은 새 관찰·수동 검토 |

| 가격 | 신규 projection에는 가격 없음. 기존 가격 제안은 별도 구조 | 후속 가격 연동 때 옵션 대응과 별도의 가격 시각/TTL을 승인해야 함. 미확인/오래된 가격은 확정 가격으로 노출하지 않음 |

24시간은 **현재 구현의 임시 안전 상한**이며 확정된 사업 요구사항이나 판매처가 보장한 유효기간이 아니다.
하루마다 상품이 바뀐다는 주장도 아니다. 더 긴 기간을 정당화하는 실측/공급자 보장이 없으므로 이번에는 그대로 유지한다.
향후 상품 정체성의 사건 기반 검토와 판매 옵션의 주기적 확인을 더 세분화할 수 있으나 별도 설계/승인 없이 구현하거나 기간을 연장하지 않는다.
현재 seller 관찰 ID는 옵션 근거와 재고 근거를 함께 참조한다. 새 재고 관찰 ID로 교체하면 identity_revision도
바뀔 수 있으므로 완전히 독립된 재고 갱신 feed가 이미 있다고 가정하지 않는다. 기존 관찰의 재고만 변경하는
경우와 새 관찰 교체를 구분하며, 독립 재고 관찰/수집 경로는 후속 설계 결정이다. 기본 unknown 운영은 이 갱신을 강제하지 않는다.

## 4. 만료 후 응답과 재확인 절차

- 동일성/판매 옵션 기한이 지나면 공개 RPC는 빈 목록을 반환한다. 저장된 원본·관찰·감사는 보존하며,
  조회로 status를 바꾸거나 감사 로그를 쓰지 않는다. 재고가 in_stock이어도 이 경계를 우회하지 못한다.
- 과거 요청의 기한/관찰이 만료되면 관리자 API는 검증 오류(현재 router에서는 HTTP400)를 반환한다.
  상태 기반 already_applied는 검증이 계속 유효할 때만 가능하며 영구 요청 영수증이 아니다.
- 유효한 근거를 가진 오래된 revision은 conflict 결과다. 이미 무효한 근거라면 revision 비교 전에 검증 오류가 날 수 있다.
  둘 다 제품/연결/감사 추가 쓰기는 없다. 클라이언트가 오류를 성공으로 간주하면 안 된다.
- 재확인은 (1) 최신 제품/연결 revision 재조회 (2) 상품/선택 옵션/포장 실제 확인 (3) 새 시각·출처·ID·내용의 seller 관찰 기록
  (4) 제품 식별이 달랐으면 새 target 스냅샷 관찰 (5) 정상 관리자 API로 현재 revision과 새 관찰 ID 및 기한 제출
  (6) 결과·감사·공개 projection 확인 순서다. 원본 URL을 바꾸려면 기존 원본을 덮지 않고 새 연결 검토가 필요하다.
- 실패/접속 차단 시 과거 관찰 시각만 갱신하거나 성공 기한을 연장하지 않는다. 만료 후 연결 없음이 안전한 fallback이다.
  클릭 직전 외부 API 호출은 필수가 아니다. 가격·재고 응답 실패를 동일성 확인 성공으로 해석하지 않는다.

## 5. 현재 운영 가능성 및 권고안

기존 관리자 제품 사실 저장은 barcode/kcal/영양정보를 처리하며, scan 재시도는 라벨 추출 목적이다.
기존 가격 수집/제안도 productId 기준이지 이 연결의 8개 SKU 식별값과 옵션 3개 ID를 재검토하는 경로가 아니다.
어느 것도 신규 `purchase_product_identity_v1`과 seller 옵션 관찰을 수집·승인하는 수단으로 대체할 수 없다.

**권고: 이번 Draft를 운영 활성화하지 않고 제한된 파일럿을 위한 정상 관리자 재확인 경로부터 별도 마련한다.**
현재 상한에서 N개를 계속 공개하려면 대략 하루 N건의 **새 유효 관찰/재확인 처리**가 필요하지만,
그것을 사람이 N개 상품 페이지를 매일 열어야 한다는 운영 요구로 삼지 않는다.
초기 사람이 확정한 SKU 기준에 새 관찰을 자동 대조하고 예외만 검토하는 후속 흐름을 7절에 제안한다.
현재 수집 경로는 그 기준을 충족하지 못한다. 따라서 전체 카탈로그 수동 재확인이나 근거 없는 자동 갱신 대신
승인된 API의 필드/접근 범위를 먼저 입증하고 소수 파일럿으로 처리량을 측정한다.
실패 시 만료/보류를 허용하며 24시간 무중단 구매 연결을 보장하지 않는다.

남은 승인 결정: 신뢰할 근거 수집 주체/정상 저장 경로, 스냅샷 생성·검토 감사, 검토 담당자와 일일 처리량,
실패·품절 재확인 정책, 독립 가격 TTL. 첫 버전 삭제 정책은 위의 물리 삭제 거부/비노출 관리로 확정한다.
UI·외부 API 자동화·운영 적용은 이 문서만으로 승인되지 않는다.

## 6. 24시간 상한의 작업량과 최소 재확인 흐름 (설계만)

유효기한은 승인 시각뿐 아니라 실제 seller 관찰 시각+24시간에도 제한된다. 수집 후 검토 지연은 남은 시간을
줄인다. 매일 같은 시각에 정확히 한 번 처리하면 연속 노출을 보장할 수 없으며 만료 전 여유/주말 담당자가 필요하다.
실제 작업 시간은 아직 측정하지 않았다. 아래는 **전량 수동 처리 시 1연결/일, 검토 5분**이라는
부담 비교용 가정이며 실측이나 권고 운영 방식이 아니다. 자동화 후의 인력 계산은 7절을 따른다.

| 활성 연결 N | 일 기본 검토 시간 | 재시도/재조사 20% 포함 | 1인 순수 검토 6시간/일 대비 |
| --- | --- | --- | --- |
| 10 | 50분 | 1시간 | 0.17명분 |
| 50 | 4시간10분 | 5시간 | 0.83명분 |
| 100 | 8시간20분 | 10시간 | 1.67명분 |
| 500 | 41시간40분 | 50시간 | 8.33명분 |

일 작업량은 N × 회당 분 × (1+재검토율) / 60이다. 3분이면 표의 0.6배, 10분이면 2배다.
초기 제품 근거 수집·변경 제품의 재식별·접속 실패 대기·휴일 교대는 별도다.
권고: 담당자/휴일 대응이 정해진 최대10개 파일럿부터 실제 시간을 측정하고, 만료6시간 전 신규 관찰 수집/예외 큐를 준비한다.
처리 여력이 없으면 연결 만료를 허용한다. 기간 연장·자동 연명으로 SLA를 맞추지 않는다.

최소 후속 흐름(이번 PR에서 UI/수집기/서버 action 추가 없음):

1. 정상 관리자 세션 검증 후 현재 제품 식별 스냅샷·연결 revision·기한을 읽는다. 토큰은 저장/로그하지 않는다.
2. 실제 판매 페이지/선택 옵션을 새로 조회한다. 최종 URL, product/item/offer ID, 선택 옵션 원문,
   맛·단위 용량·포장 수량·세트 구성·개정 표시와 수집 시각/출처를 새 관찰로 기록한다.
   단축 링크 재사용·검색 결과·이전 캡처의 날짜 수정은 새 관찰이 아니다.
3. 기존 제품 근거 스냅샷과 현재 제품이 다르면 공식 제품/포장 근거로 새 target 관찰도 수집·검토한다.
   현재 DB 필드만 복사해 공식 확인으로 간주하지 않는다. 근거 저장 경로는 인증/허용 필드/감사가 필요하다.
4. 최초 대응/식별정보 변경/불완전 근거는 관리자가 실제 선택 옵션까지 대조한다.
   후속 무변경 재확인은 7절의 모든 조건을 통과한 건만 묶어 승인 검토하고, 예외는 개별 승인/불일치/보류한다.
   현재 구현에 자동 관찰 수집/묶음 승인 기능이 있다는 뜻은 아니다. 승인 대상의 제품 revision,
   관찰 ID·내용 fingerprint가 검토 뒤 바뀌면 다시 검토한다. 기존 SQL의 최신값 검증을 우회하지 않는다.
5. 정상 admin-write 저장 경로로 expected_revision과 새 관찰 ID를 제출한다. verified 기한은 새 관찰 기반
   최대24시간을 지키고, 재고는 별도 unknown을 기본으로 둔다. 가격은 이번 응답/흐름에 포함하지 않는다.
6. 상태·감사·공개 최소 응답을 재조회한다. 충돌은 재검토하고, 불명확한 응답은 상태부터 조회한다.
   재전송은 상태 기반이며 영구 요청 중복 제거가 아니다. 실패/차단이면 만료 후 공개 제외를 유지한다.

자동화 가능(후속): 기한 큐/알림, 허용된 공개 페이지의 신규 관찰 수집, URL/ID/문자열 diff,
스냅샷 불일치·기한·중복/권한 검증, 감사 대조. 접근 제한을 우회하거나 자동 승인하지 않는다.
사람 판단 필수: 최초 상품/옵션 대응, 이미지/표기 변경의 의미, 맛·용량·세트/증정 구성과 선택 옵션의 동일성,
개정판/판매자 변경의 영향, 출처 신뢰성 및 모호한 항목의 승인/보류.
기계 파싱 성공/재고 있음은 상품 동일성 승인 근거가 아니며 과거 근거의 시각만 갱신하는 경로는 만들지 않는다.

## 7. API로 가능한 재확인과 예외 중심의 최소 운영안

조사일: 2026-10-31 (KST). 공개 명세와 저장소 코드만 확인했다. 운영 DB/배포 설정의 실제 key 존재·권한,
실제 인증 API 응답은 조회하지 않았다. API가 문서에 존재하는 것과 현재 베로로에서 사용할 수 있는 것은 다르다.

### 7.1 현재 경로와 명세상 후보

| 경로 | 확인된 정보/접근 | SKU 재확인에 대한 결론 |
| --- | --- | --- |
| 현재 `coupang-price-sync`의 Partners 검색 | `CoupangProduct`는 productId/productName/productPrice/productUrl만 소비. 검색 상위20개에서 기존 productId만 비교하고 가격 제안을 생성한다. 옵션 ID/8개 동일성 항목/현재 제품 스냅샷을 수집하지 않는다 | 가격 탐색 보조일 뿐 verified 갱신 근거가 아님. URL 쿼리에 옵션 ID가 있더라도 옵션 내용 확인을 대체하지 못함 |

읽기 전용 재확인 도구로 실행하지 않았다. `supabase/config.toml` 선언은 배포/키/실행 성공의 증명이 아니다.
저장소 workflow에서 이 함수의 정기 자동 호출은 확인되지 않았으며 운영 스케줄 유무는 미조회다.

  빈 속성 및 시스템 추출 값도 가능하므로 필드 존재만으로 확정하지 않는다.

  이 판매자 API의 sellerProductId와 같은 필드가 아니다. 이름이 비슷하다고 대입하지 않는다.
- [Partners 공식 Open API 진입](https://partners.coupang.com/#help/open-api): 상세 권한/스키마 확인은 미완료다.

### 7.2 자동 무변경 재확인 후보가 되기 위한 AND 조건 (설계, 미구현)

1. 사람이 최초 확정한 제품/옵션의 버전 있는 기준 근거가 존재하고 현재 제품 식별 스냅샷과 일치한다.
2. 정당하게 접근 가능한 신뢰 출처에서 **이번에 새로 취득한** 원문/응답, 실제 관찰 시각, 출처 URL,
   parser/schema 버전과 내용 해시를 남긴다. 캐시 응답/304는 신규 SKU 확인으로 간주하지 않는다.
   이전 관찰의 retrieved_at 수정·원문 재저장·접속 성공만으로 신규 증거를 만들지 않는다.
3. 실제 선택된 노출 productId/itemId/vendorItemId와 목적지가 기준 연결에 정확히 대응한다.
   판매자 API의 별도 등록상품 ID는 검증된 매핑이 필요하다. ID가 존재하는 것만으로 통과하지 않는다.
4. 새 응답의 브랜드/라인/맛/단위 용량/포장 수량/구성/옵션/개정 정보가 모두 명시적이고 기준과 같다.
   unknown/빈값을 not_applicable로 메우지 않는다. 대상 동물·생애주기·제형·패키지 개정에도 변화가 없어야 한다.
   비교는 버전 있는 검증기로 수행하고 이름 유사도/LLM 추정/사진 URL 동일성으로 빈 SKU 필드를 보충하지 않는다.
5. 제조사/공식 제품 기준의 유효성, 공급자 응답의 범위와 누락 탐지, 새 구성/증정품의 포착 가능성이 검증되어야 한다.
   API에 필수 정보가 없거나 제목에서만 추정해야 하면 자동 경로의 대상이 아니다.
6. 최신 revision/관찰 current/TTL/출처 내용 검사를 통과하고 승인과 감사는 서버 트랜잭션에서 함께 기록한다.
   재고/가격 변화는 별도 사실이며 그 확인으로 동일성 시한을 연장하지 않는다.

현재 API 경로로 이 조건들을 충족한다고 입증된 건수는 **미확인**이다. 자동 재확인이 이미 가능하거나
완성됐다고 보고하지 않는다. 기존 SQL의 필드/fingerprint 검사는 근거의 진실성을 대신 인증해 주지 않는다.
또한 내용 해시가 같다는 사실만으로 상품의 숨겨진 개정을 검출할 수 있는 것은 아니다.

### 7.3 최소 인증·검토 흐름과 사람이 맡을 범위

- 정상 관리자 로그인 한 번으로 재확인 작업을 시작한다. 수집 결과는 새 관찰/차이/누락 사유가 있는 제안이며,
  임의 service-role 직접 호출이나 기존 관리자 토큰을 장기 저장하는 배치 작업은 만들지 않는다.
- 위 조건을 모두 입증한 무변경 건만 `자동 재확인 가능`으로 묶고, 관리자는 처리 요약/표본을 확인해 승인한다.
  매일 사람이 전 상품 페이지를 순회하는 모델이 아니다. 필수 정보가 빠진 건을 묶음 승인에 섞지 않는다.
  초기 기준 승인 및 변경/미확인 건은 실제 근거를 사람이 개별 검토한다.
- 처음부터 무인 자동 저장을 도입하지 않는다. 후속 무인화는 승인 정책, 별도 작업 인증/최소 권한,
  서버 검증·감사 및 정지 스위치가 별도 검토돼야 한다. 현재 admin-write는 관리자 세션 인증 경로이며
  무인 작업자 인증·수집기·묶음 관찰 승인 API는 구현돼 있지 않다.
- 사람에게 넘김: 상품/옵션 ID 변경, 링크 교체/검색 도착, 맛/용량/구성/생애주기/제형/개정 차이,
  빈 속성·증정 구성 미제공·출처 간 불일치, 이미지/표기 의미 변화, parser 버전 변경·형식 변화,
  권한/접속 실패로 내용 확인 불가, 현재 제품 변경 또는 승인 revision 충돌.
- 단순 일시 장애는 제한된 재시도 후 보류하며 과거 증거를 연명하지 않는다. 업무 담당자가 없거나 근거가
  부족하면 그대로 만료시켜 공개 구매 연결을 숨긴다. 검색 링크나 다른 옵션으로 fallback하지 않는다.

초기 승인 이후 하루 사람 검토 건수의 용량 가정:
`N × [(1-q) + q×e + q×(1-e)×s]`, q=완전한 신규 근거 확보 비율,
e=그중 변경/예외 비율, s=무변경 통과 건의 표본 검토 비율. 중복 집계를 하지 않는다.
예를 들어 N=100, q=0.9, e=0.1, s=0.02라면 약20.62건/일이다.
5분/건이면 약103.1분에 묶음 요약 승인/관리 고정 시간을 더한다. 이 수치는 성과 예측이 아닌 계산 예시이며
q/e/s는 아직 실측되지 않았다. 현재 정보가 부족해 q가 낮으면 전량 수동 운영으로 확장하지 않고 출처 문제부터 해결한다.

### 7.4 파일럿과 주기 결정

1. 운영 활성화에 앞서, 별도 승인된 정상 API의 읽기 전용 샘플로 필수 ID/SKU 필드·허용 범위·호출 한도·
   재배포 없는 접근 가능성을 확인한다. 현재 코드의 가격 함수를 대신 실행하지 않는다.
2. 최초 식별이 확실하고 단일 옵션인 최대5~10개를 7~14일 관찰하는 소수 파일럿을 제안한다.
   먼저 shadow 비교/제안만 만들고, 저장/CTA 활성화는 별도 승인한다. 표본이 작다는 한계를 기록한다.
3. 수집 완전성 q, 옵션/구성 변경 검출, 접근 실패/제한 비율, parser 오탐·누락, 검토 시간의 중앙값/상위95%,
   승인 지연, 예외 큐 크기·최대 대기, 만료로 숨겨진 시간, 표본의 오일치 여부를 측정한다.
   파일럿에서는 무변경 결과도 전수 교차 검토해 자동 판정 신뢰도를 먼저 측정한다. 이후에만 표본 정책을 결정한다.
4. 갱신 큐는 임시 상한 내의 여유 시간에 시작하고, 401/403·429·형식 변화·SKU 불일치는 자동 갱신을 중단한다.
   잘못된 대응을 발견하면 해당 출처/동일 parser 경로의 자동 처리를 멈추고 기존 연결도 검토 대상으로 돌린다.
   타임아웃/불명확한 저장 결과는 상태/감사를 먼저 조회하며 무조건 재전송하지 않는다.
5. 정식 주기는 제품 동일성(변경 사건/공식 개정), 판매 옵션(변경 빈도/공급자 보장), 재고, 가격을 나누어 결정한다.
   측정된 변경률, 변경 통보/webhook 유무, 최대 미탐지 허용시간, 소비자 위험, API 약관/한도, 운영 비용을 근거로 삼는다.
   관찰 기간 중 변경이 없었다는 이유만으로 장기 동일성을 보장하지 않는다. 필요한 독립 갱신 모델도 별도 검토한다.
